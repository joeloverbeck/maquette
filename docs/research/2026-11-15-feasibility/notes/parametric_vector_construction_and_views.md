## 1. Architecture A: pure 2D per-view templates (parameter-driven control points, part libraries)

### Takeaway
Part-library avatar generators (DiceBear, facesjs) are discrete-variant pickers with affine placement; none of the ones found does continuous shape morphing or multiple views. Adding sliders is easy in code (2D blend shapes or landmark-driven warps), but nothing in a pure-2D design keeps front / three-quarter / side templates in agreement: the only documented mechanism for that is tying every stroke to a shared 3D anchor, which is already Architecture B.

### Cited Findings
- DiceBear builds each avatar as an SVG assembled on request; a style is a declarative JSON definition containing a canvas, components, colours and attributes; each component has named variants picked by a deterministic PRNG from a seed; the definition contains no code or functions. [S] — [How avatars are made](https://www.dicebear.com/understand/how-avatars-are-made/), [Definition Schema Reference](https://www.dicebear.com/specification/definition-schema/)
- DiceBear recommends authoring styles with a Figma plugin (hand-written JSON also possible); the core is described as MIT-licensed; individual artist-made styles carry their own licences. [S] — [Create an avatar style from scratch](https://www.dicebear.com/create-styles/from-scratch/), [Why DiceBear](https://next.dicebear.com/why-dicebear/)
- facesjs (zengm-games) is a JavaScript library that generates vector cartoon faces and exports SVG strings; licence Apache-2.0. [S] — [facesjs](https://github.com/zengm-games/facesjs)
- A Red Blob Games experiment generates faces by building a Bézier spline through a hypercube parameter space (continuous sliders over a face), which is the closest found example of continuous parametric morphing of a 2D cartoon face. [S] — [Procedural Face Generator](https://redblobgames.com/x/1845-face-generator)
- alec-deason/face_generator is a template-based procedural face generator that derives many faces from a small set of hand-drawn feature prototypes. [S] — [face_generator](https://www.github.com/alec-deason/face_generator)
- The 2.5D paper states why naive interpolation between independently drawn views fails: "A naive approach would be to do simple 2D shape interpolation across the key views for each stroke", but strokes move along non-linear paths at varying speed during rotation and their Z-ordering changes, which "simple 2D interpolation ignores". [V] — [Rivers, Igarashi & Durand 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- The same paper cites the standard shape-interpolation tools a 2D template system would use: as-rigid-as-possible shape interpolation (Alexa, Cohen-Or & Levin 2000) and as-rigid-as-possible shape manipulation (Igarashi et al. 2005). [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- A search for an open-source project combining Bézier sliders, SVG output and a cartoon face returned no repository that does all three; facesjs was the closest fit. [S] — [facesjs](https://github.com/zengm-games/facesjs)

### Inferences
- **How continuous morphing is added to a part library.** Two workable schemes: (1) *2D blend shapes*: every variant of a part shares one topology (same path count, segment count, point order); control points = base + Σ slider × delta. This is linear, trivially fast, and exactly what 3D morph targets do. (2) *Landmark-driven warp*: sliders move a small set of named landmarks (chin, jaw corner, eye-line, cheekbone); a smooth warp (moving least squares, thin-plate spline, or a coarse Bézier lattice as in Live2D) carries all control points. Scheme 2 lets parts with different topologies ride on the same proportions; scheme 1 gives finer control of each curve. A sensible design uses 2 for global proportions and 1 for per-part shape.
- **The DiceBear lesson is negative for this project**: its parts are swappable only because every variant is drawn in place on a shared canvas with a fixed head. Once jaw shape or eye-line height become continuous, every part needs an anchor frame (origin, scale, rotation, and usually a clip region) computed from the head model. That is the piece DiceBear does not have. (I could not confirm any anchor-point mechanism in DiceBear's schema; see Gaps.)
- **Cross-view agreement is the unsolved part of A.** With V views and N sliders, every slider's effect must be authored V times and nothing checks that "eye-line height +10%" means the same thing in the side view as in the front view. The only principled check is to require that each named landmark's 2D position in every view is the projection of one 3D point (the Rivers anchor-position construction, section 2); the residual of that fit is a measurable disagreement score. Once that is in place the system is no longer pure 2D.
- **Difficulty**: code easy (rough estimate 1.5–3k lines for templates, blending, anchoring, SVG emit); art and consistency hard. It yields only the discrete authored views, no in-between angles.

### Gaps
- Whether the current DiceBear definition schema has per-component anchors/offsets was not confirmed; I only saw the top-level structure (canvas, components, colours, attributes).
- [R] facesjs's face object, as I recall it, holds per-feature ids plus a few continuous values (`fatness`, feature `size`, `angle`) applied as affine transforms, not as curve morphs. Not re-checked this session.
- [R] Canonical references for the warps, not fetched this session: Schaefer, McPhail & Warren, "Image Deformation Using Moving Least Squares" (SIGGRAPH 2006); Bookstein's thin-plate splines (1989).
- No source found that discusses keeping independently drawn turnaround templates in numerical agreement outside the 2.5D literature.

## 2. Architecture B: 2.5D models (Rivers et al. 2010 and follow-ups, Live2D, Inochi2D)

### Takeaway
Rivers et al. interpolate each stroke's 2D shape across hand-drawn key views while rotating a per-stroke 3D anchor that fixes position and draw order; three or four key views per stroke sufficed in their examples, but the paper itself lists interior lines, concave shapes and hair as failure cases. Live2D-class tools get head turns from hand-deformed warp lattices over a single front drawing and are limited to roughly ±30 degrees, so they cannot reach side or back views.

### Cited Findings
- Core mechanism: "a stroke's shape is determined by 2D interpolation across its key views, while its position and Z-ordering are determined by its associated 3D anchor position"; the model "can be conceptualized as a collection of billboards positioned in 3D space". [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Shape interpolation: key views are placed in a 2D yaw/pitch parameterisation, Delaunay-triangulated, and a stroke's shape in a new view is interpolated across the vertices of the enclosing triangle. Tilt (roll) is ignored because it is an image-space rotation. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Anchor positions are solved automatically: each key view defines a line through the stroke's 2D position along the view direction, and the anchor is the 3D point minimising distance to those lines (iterative projection starting at the origin). Strokes that must move together (pupil and eye) are grouped and share the average anchor. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Z-order comes from anchor depth, with two artist overrides drawn as polygons over ranges of the view-angle map: an *overlap tool* (stroke A above B for these views) and a *visibility tool* (stroke shown/hidden for these views). The visibility tool also supports "complementary groups of strokes that represent the same part of the cartoon in different views", used for a stylised mouth that changes design at oblique angles. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Derived key views cut authoring: any key view is mirrored to give the reverse orientation (front gives back silhouette); strokes symmetric about the vertical axis have right-facing views mirrored to left-facing; the paper says "just three or four key views" are enough for a model rotatable to any view. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Reported model statistics (Table 1): Professor 28 strokes, 3.8 key views per stroke, 17 overlap constraints; Face 18 / 3.6 / 18; Alien 32 / 3.125 / 9; Dog 14 / 3.2 / 5. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Stated limitations: "it is difficult to show interior contour or detail lines, as these are expected to merge with shape silhouettes at some point in rotation, an operation we do not support"; "shapes that are sharp or highly concave may interpolate poorly"; "Hair is a difficult case for our system as it generally falls over the head in a way that forms a concave shell"; no partial occlusion (clothing wrapped round a body); popping when Z-order flips. Their Figure 5 failure case is a hair stroke. Remedies offered: decompose into mostly convex parts joined by Boolean union, or draw more key views. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Animation: each stroke accumulates {time, orientation, shape} triples, so an animated model can still be rotated; the authors argue 2D facial animation conventions carry over directly. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- The paper is ACM TOG 29(4), 2010; MIT lists a related US patent 8,791,942. No open-source implementation surfaced in search. [S] — [MIT DSpace record](https://dspace.mit.edu/handle/1721.1/73111), [MIT Technology Licensing Office page](https://tlo.mit.edu/industry-entrepreneurs/available-technologies/25d-cartoon-models)
- Fukusato & Maejima, "View-Dependent Formulation of 2.5D Cartoon Models" (arXiv, March 2021): treats cartoon parts that have no consistent 3D position (their example is Mickey Mouse's ears) as a view-dependent deformation problem; the user authors 2D shapes at key views and distortions at other viewpoints are generated by blending. No code link on the arXiv page. [V] — [arXiv 2103.15472](https://arxiv.org/abs/2103.15472)
- Live2D Cubism's official tutorial for face turning: each part (face contour, each eye with lashes + eyeball + white, each eyebrow, nose, mouth, ears, hair) gets its own warp deformer (lattices of 2×2 to 3×3 Bézier divisions); the rigger adds three keys on Angle X and three on Angle Y and hand-shapes the lattice at the extremes; diagonals come from "Auto Generate 4 Corners" and are then fixed by hand. Perspective is done by eye: deform "so that it is slightly thinner in the back and wider in the front". [V] — [Live2D tutorial: Adding XY Facial Movement](https://docs.live2d.com/en/cubism-editor-tutorials/xy/)
- Live2D's standard Angle X and Angle Y parameters range from -30 to 30; two 3-key parameters on one object give nine keyform patterns. [S] — [Standard Parameter List](https://docs.live2d.com/en/cubism-editor-manual/standard-parameter-list/), [Keyforms (X, Y movements)](https://docs.live2d.com/en/cubism-editor-manual/keyform-xydirection/)
- Inochi2D is an open-source 2D puppet system that "works by deforming 2D meshes created from layered art at runtime based on parameters"; BSD-2-Clause; written in D with a C FFI for C/C++/Rust; loads `inx`/`inp` files; Unity and Godot bindings. [V] — [Inochi2D repository](https://github.com/Inochi2D/inochi2d), [Inochi2D docs](https://docs.inochi2d.com/en/latest/)
- Yeh et al., "2.5D Cartoon Hair Modeling and Manipulation" (IEEE TVCG 21(3), 2015): segments a single cartoon image's hair into strand regions, completes occluded parts, estimates depth order with a layering metric, and supports wind animation, editing and braiding. [S] — [author PDF](https://pradeep-pyro.github.io/papers/2.5dcartoon.pdf)
- Monster Mash (Dvorožňák et al., SIGGRAPH Asia 2020): sketch a character, inflate it to 3D, animate it; source under Apache-2.0 (third-party directory may differ); "not an officially supported Google product". [S] — [google/monster-mash](https://github.com/google/monster-mash), [project page](https://dcgi.fel.cvut.cz/~sykorad/monster_mash.html)
- Other leads surfaced by title only: Reallusion Cartoon Animator's angle-point deform settings for 360-degree heads; "Iki", a web puppet engine using warp grids and rotation deformers for a soft head turn; "Modeling Character Canvases from Cartoon Drawings" (Bessmeltsev et al., TOG 2015). [S] — [Reallusion manual](https://manual.reallusion.com/Cartoon-Animator/Content/Resources/4.0/03_Actor/Head_Types/Deform_Settings_for_Angle_Points.htm), [Iki listing](https://awesome.ecosyste.ms/projects/github.com%2Fzeikar%2Fiki), [Character Canvases](https://history.siggraph.org/?p=114420)

### Inferences
- **What must be authored for a Rivers-style model**: every stroke drawn in about 3–4 views (front, side, top or three-quarter), with explicit stroke correspondence between views, plus roughly 5–20 overlap constraints per model. For a *character creator* the cost multiplies: each part type and each slider's effect must exist in each key view. The 3D anchor gives consistent placement for free, but shape agreement is still by hand.
- **The listed limitations hit anime directly.** The jaw/cheek line, nose tick and eyelid creases are interior lines that merge into the silhouette as the head turns, which is the operation Rivers et al. say they do not support; anime hair is the concave shell they single out. A 2.5D model for anime therefore needs (a) the head outline as its own convex-ish stroke with per-view shapes, (b) hair decomposed into many near-convex clumps each with its own anchor, and (c) the "complementary group" swap for parts that change design by view (mouth in profile).
- **Live2D-style warping is not a route to four views.** Its range is about ±30 degrees from one drawing, authored by eye. It is the right model for small head motion and for animation layered on top of a view, not for producing side or back views.
- **Patent**: US 8,791,942 was filed around 2010, so it is plausibly in force into the early 2030s. An open-source project that reproduces "per-stroke 3D anchor + 2D key-view shape interpolation" literally should get this checked. This is a flag, not legal advice.
- **Difficulty**: moderate code (rough estimate 3–6k lines: view-space triangulation, point-correspondence interpolation, anchor solve, depth sort, constraint overrides). The algorithm is simple; the authored data is the cost.

### Gaps
- Inochi2D's parameter model (1D/2D parameters, keypoints, bindings) could not be read: the docs landing page links out and the fetch did not reach the parameter pages. Latest release and last-commit date were not shown on the fetched repository page.
- "Smoothie" could not be identified. [R] ToonSynth (Dvorožňák et al., SIGGRAPH 2018, example-based synthesis of hand-coloured cartoon animation) was not returned by search and is not checked here; it is a style-transfer-to-skeleton method for raster animation, not a multi-view model.
- No maintained open-source implementation of 2.5D cartoon models was found; I did not search GitHub directly with code search.
- Whether Monster Mash's repository is archived was not checked.

## 3. Architecture C: 3D proxy plus line extraction, and authored 3D feature curves

### Takeaway
Extracting clean, topologically consistent occluding contours from a mesh is a research-grade problem (ConTesse, 2023, exists because earlier methods fail), and Blender's two line engines export SVG with documented caveats; practitioners report that computed lines on anime faces lack control and put interior face lines on textures instead. The cleaner variant for this project is to author the interior feature lines as 3D Bézier curves and project them, using the 3D proxy only for silhouette and occlusion; published work (3Doodle, 2024) uses exactly that split.

### Cited Findings
- Bénard & Hertzmann, "Line Drawings from 3D Models", Foundations and Trends in Computer Graphics and Vision 11(1–2):1–159 (2019): a tutorial centred on occluding contours, covering contour geometry on meshes and smooth surfaces, extraction, visibility and stylisation, and the trade-offs between exact and hardware-accelerated methods. [V] — [arXiv 1810.01175](https://arxiv.org/abs/1810.01175)
- ConTesse (Liu, Bénard, Hertzmann & Hoshyari, ACM TOG 42(1), 2023): the abstract calls smooth contour visibility "such a challenging problem in the past" because "previous methods do not guarantee" the validity conditions; the method finds sampled contours that can be assigned consistent visibility and outputs a new triangle mesh whose contours match, from which standard view-map algorithms extract and stylise lines. Works on any triangle mesh by treating it as a subdivision base mesh. Code: github.com/squidrice21/ConTesse (licence not stated on the project page). [V] — [ConTesse project page](https://dgp.toronto.edu/~hertzman/contesse/), [arXiv 2111.06006](https://arxiv.org/abs/2111.06006)
- Blender Freestyle SVG Exporter (manual through 4.1): an add-on exporting Freestyle renders to SVG; can fill contours with material colour and write SVG animation. Caveats in the manual: Freestyle styles per point while SVG styles per path, so "a one-on-one translation between Freestyle and SVG is not possible"; fill results can be unexpected and layer ordering "is by no means perfect"; a "Split at Invisible" option improves paths broken by stroke modifiers. [S] — [Freestyle SVG Exporter, Blender 4.1 manual](https://docs.blender.org/manual/en/4.1/addons/render/render_freestyle_svg.html)
- Blender Grease Pencil SVG export (File > Export > Grease Pencil as SVG): works only in Object Mode; exports Active, Selected or Visible Grease Pencil objects; options are Sampling (stroke sampling precision), Fill, Uniform Width (constant thickness), and Clip Camera. [V] — [Blender 4.3 manual source](https://sources.debian.org/src/blender-doc/4.3-1/manual/files/import_export/grease_pencil_svg.rst)
- The current development manual for this export page is titled "Blender 5.4 Manual" (so Blender's dev branch is 5.4 as of November 2026). [V] — [Import/Export SVG as Grease Pencil, dev manual](https://docs.blender.org/manual/en/dev/files/import_export/grease_pencil_svg.html)
- Blender Line Art modifier: generates Grease Pencil strokes from a scene/collection/object as seen by the active camera. Edge types: Contour (silhouette options), Crease, Intersections, Material Borders, Edge Marks ("strokes from freestyle edge marks"), Loose (edges with no face), Light Contour, Cast Shadow. Occlusion can be selected by level (0 = visible). Chaining options include image threshold, smooth tolerance and angle splitting. Results can be baked to strokes. Each Line Art modifier runs its own full occlusion calculation, a documented performance limitation. [V] — [Line Art modifier, Blender 4.3 manual source](https://sources.debian.org/src/blender-doc/4.3-1/manual/grease_pencil/modifiers/generate/line_art.rst)
- Blender bug reports on Grease Pencil SVG export: exported strokes are not occlusion-tested ("just export all strokes, visible or not"), with the suggested fix being to generate lines with Line Art first; older reports of modifiers not applied on export, empty output with orthographic cameras, and wrong stroke thickness. These are 2021–2022 reports and may be fixed. [S] — [T86973](https://developer.blender.org/T86973), [T86942](https://developer.blender.org/T86942), [issue 103061](https://projects.blender.org/blender/blender/issues/103061)
- three.js SVGRenderer: an add-on that renders geometry as SVG; documented limitations are "No advanced shading", "No texture support", "No shadow support"; visibility is controlled only by `sortElements` and `sortObjects` (both default true) plus an `overdraw` fraction to hide anti-aliasing gaps. Intended for logos, diagrams, maps and UI. [V] — [three.js SVGRenderer docs](https://threejs.org/docs/pages/SVGRenderer.html)
- Practitioner view on anime outlines in Blender: the choices are "lack of control (line art modifier), lack of performance and lack of control (Freestyle), or lack of quality/pixelization (hand painting)". [S] — [Blender Artists master-class thread](https://blenderartists.org/t/learn-how-to-use-blender-freestyle-for-anime-outlines-master-class/1328573)
- An artist's Blender setup makes a 3D nose turn into a dot or line when the character looks straight at the camera, i.e. the nose line is camera-dependent rather than fixed geometry. [S] — [80.lv article](https://80.lv/articles/way-to-make-3d-nose-look-anime-like-in-blender)
- Guilty Gear Xrd (GDC 2015) used an inverted hull for outlines; inner lines needed a different technique because the hull does not work on surfaces, and lines drawn directly on textures pixelate in close-up, so lines were laid out with UV mapping giving control of line width. (From an AI-generated summary of the talk recording; treat as secondary.) [V, secondary source] — [talk summary](https://videohighlight.com/v/yhGjCzxJV3E), [GDC Vault entry](https://gdcvault.com/play/1022031/GuiltyGearXrd-s-Art-Style-The)
- 3Doodle (arXiv, February 2024) represents an object as two kinds of 3D strokes: view-independent feature lines modelled as 3D cubic Bézier curves, and view-dependent contours of smooth surfaces; the whole representation is under 1.5 kB. Its authors note that curve-only methods (Neural Edge Fields) cannot represent view-dependent contours. [S] — [3Doodle](https://arxiv.org/html/2402.03690v1)
- Diff3DS (arXiv, May 2024) projects 3D rational Bézier curves to 2D under perspective and rasterises them differentiably to optimise view-consistent 3D sketches. A 2025 paper on sparse 3D curve abstraction notes that occluding contours are view-inconsistent and cause flicker across dense views. [S] — [Diff3DS](https://arxiv.org/abs/2405.15305), [sparse 3D curves, arXiv 2505.04813](https://arxiv.org/pdf/2505.04813v1)

### Inferences
- **Yes, feature lines can be authored as 3D curves and projected to clean 2D Béziers.** Bézier curves are affinely invariant, so under an orthographic (or any affine) camera the projection of a 3D cubic Bézier is exactly the 2D cubic Bézier of the projected control points; under perspective it is a rational cubic (Diff3DS does this). A character sheet is naturally orthographic, so eyes, brows, mouth, nose tick, jaw rim, hairline and clothing seams can be stored as 3D control points and emitted as exact SVG `C` segments at any angle with no extraction, no fitting and no noise.
- **What a curve network cannot give is the occluding contour**: the outline of the cranium, the far cheek in three-quarter view, the neck and limb outlines are view-dependent and are not any fixed 3D curve. 3Doodle's split (fixed 3D curves plus view-dependent contours of simple smooth primitives) is the right decomposition. For a head, the contour can come from an analytic proxy (sphere/ellipsoid cranium plus a jaw surface) whose silhouette is cheap and exact, or from per-view authored outlines interpolated 2.5D-style. The join where an interior line (jaw) runs into the silhouette (cheek) is the delicate spot.
- **Occlusion for curves** needs only a depth test against a coarse proxy (hide the far ear, clip the far eye and far brow at the face edge) plus a few artist-style visibility rules keyed on yaw, the same idea as Rivers' visibility tool.
- **Mesh + Blender pipeline (C1)** is the fastest way to *see* a turnable head, but: Blender is GPL and heavy (usable as a subprocess, not as a linked library); output is polylines with per-path style, needing chaining, simplification and refitting; interior face lines are the weak part; and it moves the hard problem to "have a good parametric anime head mesh", which an AI agent cannot sculpt by placing vertices any better than it places Bézier points. It is most useful offline, to render reference turnarounds from an existing model and to supply ground-truth landmark positions per view.
- **Blender's Edge Marks are the built-in form of hand-authored feature lines**: the user marks mesh edges and both Freestyle and Line Art render them. They are tied to mesh topology, so line placement is only as fine as the edge flow. ([R] that Freestyle edge marks are user-set per mesh edge; the manual page fetched only says Line Art generates strokes from them.)
- **three.js SVGRenderer is not a hidden-line renderer.** It emits depth-sorted filled polygons; it does not produce chained contour strokes, so it does not solve this problem.
- **Difficulty**: projecting curves is easy; analytic silhouette of a simple proxy is easy to moderate; robust general mesh contours are hard (do not write this yourself); ConTesse is research code, not a library.

### Gaps
- Freestyle SVG Exporter's status after Blender 4.2 moved bundled add-ons to the extensions platform was not confirmed; manual pages found stop at 4.1.
- Whether current Blender (5.x) applies Line Art on SVG export without baking was not confirmed; the bug reports are from the 2.9x–3.x era.
- Pencil+ 4 Line vector output: no source read this session.
- ConTesse's code licence and runtime were not found on the project page.
- [R] Suggestive contours (DeCarlo et al., SIGGRAPH 2003) and apparent ridges (Judd, Durand & Adelson, SIGGRAPH 2007) add view-dependent interior lines from surface curvature. They were designed for detailed scanned or sculpted surfaces; on a smooth low-poly anime face they would have little signal, and where they fire they are not where an anime artist puts the line. Not fetched this session; the survey above covers both.
- No project was found that ships a parametric anime head as a 3D curve network rendered to SVG. Grease Pencil strokes drawn on a surface are true 3D curves in Blender, but per the bug report above their SVG export is not occlusion-tested.

## 4. The view-dependent "cheat" problem

### Takeaway
The accepted solution since 1999 is to store view-specific corrections keyed on camera direction and blend them: Rademacher's view-dependent geometry in 3D, Fukusato & Maejima's formulation for 2.5D, camera-driven shape keys in Blender practice, and per-frame hand deformation at Arc System Works. A parametric system can encode cheats the same way, as per-view deltas on landmarks and curves blended over yaw/pitch.

### Cited Findings
- Rademacher, "View-Dependent Geometry" (SIGGRAPH 1999, pp. 439–446): a base model plus key deformations plus key viewpoints tying each reference drawing to the base; for an arbitrary viewpoint the key deformations are interpolated to give a view-specific model, capturing distortions in cel-animation reference drawings that a single 3D model cannot. [S] — [SIGGRAPH history archive entry](https://history.siggraph.org/?p=116416), [paper PDF](https://www.cs.princeton.edu/courses/archive/fall00/cs597b/papers/rademacher99.pdf)
- Rivers et al. motivate 2.5D with the same point: rendering from a single 3D model "cannot account for" cartoon stylisation, and view-dependent geometry addresses it by providing different models per view. Their own mechanism for a mouth that changes design by angle is complementary stroke groups switched by a visibility range, plus turning off mirrored derived views for "strokes which have inconsistent appearances across different views, such as the mouth". [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Fukusato & Maejima (2021) explicitly recast 2.5D cartoon models as a view-dependent deformation problem for parts with no consistent 3D position; the user draws the part at key views and the system blends. [V] — [arXiv 2103.15472](https://arxiv.org/abs/2103.15472)
- El Mqirmi & Aigerman, "View-Dependent Deformation Fields for 2D Editing of 3D Models" (arXiv, April 2025): the user picks viewpoints and deforms the object in each view's 2D image plane; the method builds a deformation field that interpolates these 2D edits smoothly over viewpoint, composes edits like layers, and applies to meshes or Gaussian splats; applications include cartoon effects and fitting 3D models to sketches. No code link on the page. [V] — [arXiv 2504.05544](https://arxiv.org/abs/2504.05544)
- Blender practice: the CamKeys add-on (formerly Cam-Shape-Matic) drives shape keys from camera angle or distance, with as many captured angles as needed, and is sold for fixing anime faces whose side profiles do not match their front. A 2016 tutorial covers view-dependent face rigging in Blender. [S] — [CamKeys](https://blendermarket.com/products/camkeys), [Lesterbanks 2016](https://lesterbanks.com/2016/05/view-dependent-face-rigging-blender/)
- A Blender Artists thread describes the profile-mouth problem directly: an anime mouth needs different shapes from front and side, and blend shapes relative to one basis cannot hold both. [S] — [Blender Artists thread](https://blenderartists.org/t/how-to-change-animate-basis-shape-key/1122928)
- Guilty Gear Xrd (Motomura, GDC 2015), from an AI-generated summary of the recording: guiding principle "killing everything 3D"; hand-edited vertex normals on faces are "essential" for a clean look; rigs have "approximately 500 bones per character"; scale animation was done manually; mesh deformation at every keyframe keeps the model from looking rigidly 3D; limited animation with each frame treated as a key, like stop motion. [V, secondary source] — [talk summary](https://videohighlight.com/v/yhGjCzxJV3E)
- Contemporary Japanese coverage of the talk: characters are about 40,000 polygons, no normal maps, and cel shading is controlled entirely by designers. The talk and an English handout PDF were published by Arc System Works. [S] — [Game Watch, March 2015](https://game.watch.impress.co.jp/docs/news/20150307_691725.html), [Arc System Works announcement](https://www.arcsystemworks.com/guilty-gear-xrd-art-talk-at-game-developers-conference-2015/)
- Live2D riggers apply perspective by hand per part at the extreme keys rather than by projection. [V] — [Live2D tutorial](https://docs.live2d.com/en/cubism-editor-tutorials/xy/)

### Inferences
- **Encoding for a parametric system**: keep one 3D-consistent base (landmarks and feature curves), then add a table of *view corrections*: for each named key view (front, three-quarter, side, back, optionally up/down) a set of 2D offsets or replacement shapes for specific elements, blended by the same yaw/pitch triangulation Rivers uses. Typical entries: mouth slides toward the visible cheek and switches to a profile design at high yaw; far-cheek contour gets its characteristic bulge below the far eye in three-quarter; far eye narrows less than true projection and is shifted; nose switches from dot/tick to profile wedge; ears and hairline shift.
- **Corrections must compose with sliders.** If corrections are stored as absolute shapes they break when the jaw slider moves. Store them relative to the landmark frame (as offsets in a local coordinate system of the part, or as extra blend-shape deltas multiplied by a view weight) so they ride along with proportions.
- **Three mechanisms cover every case found**: continuous delta blending (cheek bulge, eye squash), discrete swap with a visibility range (profile mouth, profile nose), and Z-order overrides (hair locks passing in front of or behind the face).
- **Difficulty**: the mechanism is easy (a weighted sum keyed on view). Getting the corrections to look right is taste-dependent and is where reference drawings or a human eye are required. This is the piece an agent placing points blind has the least chance of getting right, and the piece where fitting to references (section 9) pays most.

### Gaps
- The Guilty Gear Xrd handout PDF (ggxrd.com) refused the connection, so per-camera face handling and limb scaling to fake perspective are not confirmed from the primary slides; the summary used is machine-generated.
- No paper titled or scoped as "view-dependent deformation for anime faces" specifically was found; the closest are the two cited above.
- No quantitative description of anime's three-quarter conventions (how much the far eye narrows, where the mouth sits) was found in a citable source.

## 5. Eyes

### Takeaway
No published parametric anime-eye generator for vector output was found; what exists is shader/texture-based Blender products and Live2D's convention of one small warp lattice per eye. The eye parameterisation therefore has to be designed for this project, and on head turns the far eye should be handled as an authored per-view shape, not a projection.

### Cited Findings
- A targeted search for parametric/procedural anime eye generators (vector lash curves, iris parameters) returned no paper or open repository; results were commercial Blender shader packs with adjustable iris size and width and animated pupils/highlights, and a patent on a parametric *realistic* eye model. [S] — [Procedural Anime Eye Shader Pack](https://superhivemarket.com/products/anime-eye-shader/docs), [US10217265B2](https://patents.google.com/patent/US10217265)
- Live2D's tutorial groups each eye's lashes, eyeball and white under one warp deformer, recommends 3×3 divisions with "the four inner control points surround[ing] the eye", and has the rigger hand-shape the lattice at the Angle X/Y extremes so the far side is "slightly thinner". [V] — [Live2D tutorial](https://docs.live2d.com/en/cubism-editor-tutorials/xy/)
- Rivers et al. group pupil and eye strokes under a single shared 3D anchor so they do not drift apart during rotation. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- A current cartoon landmark detector documents that its six-points-per-eye scheme forces "very round cartoon eyes [into] an almond shape", evidence that standard landmark schemes under-describe anime eyes. [V] — [MDFLD](https://github.com/zenonLEE/MDFLD)

### Inferences
- **Proposed parameter set (design proposal, not sourced)**: eye box (centre on the eye line, width, height, inter-eye gap as a fraction of head width); tilt (outer-corner raise); upper lash line as two or three cubic segments with a thickness profile (thin at inner corner, heavy over the iris, flick at the outer corner); lash wing length and angle; optional crease line offset; lower lid as absent / outer-third only / full, with its own curvature; sclera shape as the region between lids; iris as an ellipse (height-to-width ratio, size relative to the opening, vertical position so the upper lid clips it); pupil scale and shape; highlight count, sizes and positions; iris gradient bands; lash and iris colours. Roughly 20–30 scalars plus a few discrete style choices.
- **Left/right handling**: mirror geometry, but not highlights or gaze. [R] The usual drawing convention is that highlights sit on the same screen side in both eyes because they represent one light source.
- **Head turns**: project the eye's anchor in 3D for position, then apply an authored view correction for shape: horizontal compression of the far eye that is weaker than cos(yaw), a shift toward the nose bridge, clipping by the face contour, and the iris kept as a clean ellipse. In side view the eye becomes a different shape entirely (a wedge with the iris as a narrow ellipse), which is a discrete swap, as with the mouth.
- **Why eyes deserve their own module**: they carry most of the style identity, they are small closed shapes with layered fills and clips (sclera clip, iris, pupil, highlights, lash on top), and they animate (blink, gaze). A blink is one more blend shape on the lid curves; gaze is a translation of iris and pupil inside the sclera clip. Both are easy once the eye is built from named curves.
- **Difficulty**: code moderate; aesthetic tuning hard and high-value. A handful of hand-designed eye presets expressed in the parameter space will do more than wide random ranges.

### Gaps
- No paper or dataset giving statistics of anime eye proportions (iris ratio, eye height vs face height by style or era) was found.
- [R] Live2D's standard parameter list includes eye-open, eye-smile and eyeball X/Y parameters; only the Angle X/Y ranges were seen this session.

## 6. Hair

### Takeaway
Every source that handles anime hair well treats it as many separate strands or cards along guide curves (VRoid's procedural and freehand groups; CHARM's control-point hair cards trained on 37K VRoid hairstyles), while the one multi-view 2D system examined names hair as its failure case. Hair is the hardest part to make look designed, and the evidence points to parametrised hand-designed clumps, not free generation.

### Cited Findings
- Rivers et al.: hair "generally falls over the head in a way that forms a concave shell", interpolates poorly between key views, and should partly disappear behind the head during rotation, which their model does not support; fixing it needs "either a high number of key views or a decomposition into many sub-parts". [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- VRoid Studio's hair editor adds "procedural hair guides" whose parameter panel covers hair count, cross-section and twist; guides have height and offset parameters; parting is controlled by Parting (Length), Parting (Side Volume) and Parting (Side Convergence); a procedural group can be converted to a freehand group, after which procedural parameters stop applying but individual control points stay editable; smoothness, cross-section and thickness drive polygon count. [S] — [VRoid help: Hair Editor](https://vroid.pixiv.help/hc/en-us/articles/360012339194-Hair-Editor), [stray hair, procedural version](https://vroid.pixiv.help/hc/en-us/articles/360013259773-How-to-model-stray-hair-Procedural-Hair-ver), [changing a hair part](https://vroid.pixiv.help/hc/en-us/articles/360013209794-How-to-change-a-hair-part), [reducing hair polygons](https://vroid.pixiv.help/hc/en-us/articles/360013210674-How-to-decrease-the-number-of-hair-polygons)
- A Japanese-language paper on sketch-based hair modelling describes VRoid Studio as placing hair cards along sketch input on a mesh that covers the head, with shapes then tuned through parameters or curves. [S] — [Art and Science journal v23n1](https://art-science.org/journal/v23n1/v23n1-1/artsci-v23n1-1.pdf)
- CHARM (He et al., SIGGRAPH Asia 2025): "a sequence of control points represents each hair card", each control point encoded with five geometric parameters; an autoregressive model generates hairstyles; trained on AnimeHair, 37K anime hairstyles with separated hair cards. Project page given; no code repository linked on the arXiv page. [V] — [arXiv 2509.21114](https://arxiv.org/abs/2509.21114)
- The AnimeHair dataset is derived from publicly available VRoid models, and the representation is inspired by VRoid's hair format. [S] — [CHARM HTML](https://arxiv.org/html/2509.21114v1)
- Yeh et al. (TVCG 2015) model cartoon hair in 2.5D as layered, depth-ordered strand regions completed behind occlusions. [S] — [author PDF](https://pradeep-pyro.github.io/papers/2.5dcartoon.pdf)

### Inferences
- **Representation that fits the rest of the system**: a hairstyle is a set of *clumps*; each clump is a 3D guide curve rooted on the scalp (root position, direction, length, curl, droop) plus a 2D width profile (root width, belly, taper to tip, tip split count) and a layer (behind head, on head, in front of face). In each view the guide curve is projected and the clump outline is built as a variable-width ribbon around it (section 8). This is the 2D analogue of a hair card, gives consistent views because the guides are 3D, and sidesteps the concave-shell problem because each clump is near-convex.
- **Front/back split is mandatory**: hair behind the head, hair cap on the cranium, and fringe/sidelocks in front of the face are separate layers with different Z relative to the face; the fringe must also clip against nothing while the back hair is occluded by head and shoulders.
- **Why generated hair looks generated**: designed anime hair has a hierarchy (few large masses, then medium locks, then one or two stray accents), deliberate rhythm in tip spacing and direction, and a clean overall silhouette. Uniform random guide parameters produce even spacing and no hierarchy. VRoid's own workflow (procedural groups converted to freehand for final control, and a marketplace of hand-made presets) suggests that even with a guide system, the designed unit is a hand-authored style.
- **Practical approach**: ship a small library of hand-designed hairstyles, each expressed as clump lists with a few exposed sliders (length, volume, fringe length, parting side, curl), rather than a hairstyle generator. Sliders modulate a designed style; they do not create one.
- **Difficulty**: ribbon geometry moderate; layering and occlusion moderate; making it look good is the hardest aesthetic problem in the project and the one with least automation support. Interior hair lines (strand detail lines, highlight shapes) add another authored layer.

### Gaps
- No paper on procedural 2D vector anime hair was found; all generation work found is 3D (cards or strands).
- The official list of VRoid procedural hair parameters was not read in full; details above come from search summaries of help pages, some several years old.
- CHARM code/dataset release status and licence were not confirmed (the CC BY-NC-SA notice on arXiv is the paper's licence).
- No evidence was found quantifying how users judge procedural versus hand-designed anime hair.

## 7. Body and clothing

### Takeaway
An anime-specific SMPL extension now exists (Anime-SMPL, ICLR 2026) and research notes that standard SMPL-X entangles head size with body shape, but SMPL-family licences and the 3D-mesh form make them poor direct dependencies; a skeleton plus limb-profile model is simpler for flat vector output. Layering is solved in cut-out animation by separating joint hierarchy from draw order, with limbs that cross the torso as the recurring trouble spot.

### Cited Findings
- Anime-Ready (ICLR 2026) extends SMPL into "Anime-SMPL"; shape parameters come from PCA over anime character meshes keeping the top 98 components, covering body types and facial proportions with unified topology, joints and skinning weights; the pipeline regresses these parameters from an A-pose character image. [S] — [ICLR 2026 poster](https://iclr.cc/virtual/2026/poster/10010948)
- A January 2026 paper observes that the SMPL-X shape space ties cranial features to body shape, limiting head-to-body ratio variation, and proposes decoupling head size from body shape to generalise to stylised characters. [S] — [arXiv 2601.22693](https://arxiv.org/html/2601.22693v2)
- SMPL-X requires sign-up and licence agreement before download. [S] — [SMPL-X site](https://smpl-x.is.tue.mpg.de/)
- "Anny" (arXiv, November 2025) is a recent parametric human body model surfaced by search; SOMA (2026) is an effort to make SMPL, SMPL-X, MHR, Anny and others interoperable. [S] — [arXiv 2511.03589](https://arxiv.org/abs/2511.03589), [SOMA, arXiv 2603.16858](https://arxiv.org/pdf/2603.16858)
- Cut-out rig layering, Toon Boom Harmony: draw order follows the layer list, and a layer can be nudged on the Z axis to override order while animating without restructuring the rig. [S] — [Harmony: How to Rig a Cut-out Character](https://docs.toonboom.com/help/harmony-24/premium/getting-started/character-building.html)
- Cut-out rig layering, Godot: draw order can be set independently of the joint hierarchy, with RemoteTransform2D letting a node follow a bone while living elsewhere in the draw tree. [S] — [Godot cutout animation docs](https://docs.godotengine.org/en/3.0/tutorials/animation/cutout_animation.html)
- A Harmony user wanting the upper arm behind the body and the forearm in front found that moving the forearm forward broke the automatic joint patch, the standard split-limb problem. [S] — [Toon Boom forum thread](https://forums.toonboom.com/t/layering-upper-arm-behind-body-so-forearm-is-in-front-of-body/14171)
- Rivers et al. note their model has no partial occlusion, "as with a piece of clothing wrapped around a body". [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Monster Mash inflates sketched 2D parts into a 3D model that can be animated; Apache-2.0 source. "Modeling Character Canvases from Cartoon Drawings" (TOG 2015) builds 3D proxies from a single cartoon drawing. [S] — [google/monster-mash](https://github.com/google/monster-mash), [Character Canvases](https://history.siggraph.org/?p=114420)

### Inferences
- **Recommended body model for flat vector output**: a 3D skeleton with bone lengths driven by sliders (head-to-body ratio, leg/torso ratio, shoulder and hip width, limb lengths), and for each segment a *profile*: radius as a function of position along the bone, separately for the front and side aspects (two width functions), so a limb is a generalised cylinder with an elliptical cross-section. Projecting to a view gives a centreline and a width function, and the outline is the same variable-width ribbon used for hair and strokes. Torso, pelvis, hands and feet need dedicated templates.
- **Joints**: emit each segment as a closed shape with round ends, fill all segments with the skin colour, then draw outlines only on the union boundary (a Boolean union of the filled shapes, or painter's-order fills with outlines drawn first and fills on top to hide interior lines). This removes joint seams without a mesh. Elbow and knee crease ticks are separate authored feature lines.
- **Layering**: keep a draw-order key per shape that is computed from 3D depth of the bone in the current view, with explicit overrides, exactly the Harmony/Godot separation of hierarchy from order. Limbs must be split at joints so the upper and lower halves can sit on different sides of the torso.
- **Clothing**: garments as shapes bound to the same skeleton and profiles with an offset (profile radius plus ease), with hems and openings as feature curves and a layer rank (skin, underlayer, top, outerwear). Sleeves follow the limb split. Wrap-around occlusion (collar behind neck, skirt behind legs) requires each garment to be split into front and back pieces, the standard paper-doll solution. Loose garments (skirts, coats, capes) are not derivable from limb profiles and need their own templates per view or their own 3D guide curves.
- **SMPL-family models** are useful as a source of proportion statistics or as an offline reference, not as a dependency: they are 3D meshes needing contour extraction, and their licences are restrictive. ([R] SMPL/SMPL-X are licensed for non-commercial research with separate commercial licensing; not re-read this session.)
- **Difficulty**: skeleton and limb ribbons moderate; hands and feet hard to draw well at any size; clothing is open-ended and the largest content cost after hair. Animation suitability is good, since this is a cut-out rig by construction.

### Gaps
- No source was found for a "stick figure to outlined body" capsule/ribbon algorithm in the anime context; the model above is an inference.
- Anime-SMPL's code, weights and licence were not checked. Anny's licence was not confirmed ([R] I recall it being permissively licensed and built on MakeHuman, unverified).
- MakeHuman anime targets, VRM/VRoid model licence terms and their suitability as offline references were not researched this session.
- No published dataset of anime body-proportion statistics (head counts by age/style) was found.

## 8. Line quality and SVG output

### Takeaway
SVG has no variable-width stroke, so tapered lines must be emitted as filled outline paths; the building blocks exist under permissive licences (kurbo for stroke expansion, offsetting and curve fitting; perfect-freehand for pressure-style outlines), but none of the libraries checked provides variable-width stroking of Béziers out of the box, and kurbo has no Boolean operations.

### Cited Findings
- kurbo 0.13.1 (Rust, Apache-2.0 OR MIT) provides: `stroke`/`stroke_with` expanding a stroke to a fill, with `StrokeOpts`, caps and joins; an `offset` module for offset curves of cubic Béziers; curve fitting via `fit_to_bezpath`, `fit_to_bezpath_opt` ("highly optimized" fit), `fit_to_cubic` and the `ParamCurveFit` trait; a `simplify` module; arc length and nearest-point traits. Boolean path operations and variable-width stroking are absent from the API listing. [V] — [kurbo docs](https://docs.rs/kurbo/latest/kurbo/)
- perfect-freehand (MIT) takes input points (optionally with pressure) and returns outline points forming a polygon around them, i.e. a filled variable-thickness stroke; a Rust port, freedraw, is MIT. [S] — [perfect-freehand](https://github.com/steveruizok/perfect-freehand), [freedraw](https://docs.rs/crate/freedraw/latest)
- perfect-freehand's author noted that open-source implementations of variable-width lines were scarce and pointed to Inkscape's source and browser canvas stroking code as prior art. [S] — [perfect-freehand discussion 16](https://www.github.com/steveruizok/perfect-freehand/discussions/16)
- MFEKstroke (font tooling, Rust) has a variable-width stroking mode for glyph outlines. [S] — [MFEKstroke](https://mfek.org/stroke)
- Blender's manual states the underlying mismatch: Freestyle assigns style per point whereas SVG assigns style per path, so varying thickness along a line cannot be expressed as an SVG stroke. [S] — [Freestyle SVG Exporter manual](https://docs.blender.org/manual/en/4.1/addons/render/render_freestyle_svg.html)
- Blender's Grease Pencil SVG export offers a "Uniform Width" switch and a sampling precision, i.e. it samples strokes to polylines/outlines rather than emitting fitted Béziers with a width profile. [V] — [Blender 4.3 manual source](https://sources.debian.org/src/blender-doc/4.3-1/manual/files/import_export/grease_pencil_svg.rst)

### Inferences
- **Recommended stroke model**: every line is a centreline cubic Bézier path plus a width profile w(t) (for example start taper, body width, end taper, optional pressure bumps). Outline construction: sample the centreline by arc length, offset left and right by w/2 along the normal, add caps, then fit each side back to cubics with a Schneider-style or kurbo `fit_to_bezpath` fit. Because the profile is smooth and the centreline is clean, the fit is stable and yields few segments. Keep the centreline in the SVG too (as a hidden or data-attributed path) so later rigging tools can deform the centreline and regenerate the outline.
- **If the parametric model emits Béziers directly, curve fitting from samples is needed only for derived geometry** (offset outlines, projected silhouettes, Boolean results), not for the primary shapes. This avoids the tracing-quality problem entirely, which is a major advantage over any raster or mesh-contour route.
- **Boolean operations** are needed for unioning body segments, clipping hair against the head, and merging strokes. In Rust, kurbo does not provide them; the options are polygon clippers on flattened paths followed by refitting, or a Bézier-aware Boolean library. In TypeScript, Paper.js covers stroke-free path Booleans and simplification. For many cases SVG `clipPath`/`mask` and paint order avoid Booleans altogether and keep the document editable.
- **Semantic SVG structure for later rigging**: one `<g>` per part with a stable id (`head/outline`, `eye-L/lash-upper`, `hair/fringe/clump-03`), a fixed layer order, fills and lines in separate child groups, pivots and landmarks stored as `data-` attributes or a sidecar JSON, consistent path direction and point count per part across all characters and views (this is what makes later blend-shape animation possible), and no baked transforms.
- **Difficulty**: moderate and well-trodden. The main risks are offset cusps on tight curves with wide strokes, and self-intersections at sharp corners; both are handled by limiting width relative to curvature radius and by cleaning the outline with a union.

### Gaps
- [R] Not verified this session: Schneider's "An Algorithm for Automatically Fitting Digitized Curves" (Graphics Gems, 1990) is the standard least-squares cubic fit used by Paper.js `simplify()` and many ports; potrace (Selinger 2003, GPL) fits curves to bitmap outlines and is the wrong tool when the centreline is already known; Paper.js is MIT; Clipper2 is Boost-licensed and polygon-only; Skia PathOps/PathKit is BSD-3 and does Bézier Booleans; svgpathtools (Python) is MIT; kurbo's fitting and offset code derive from Raph Levien's published work on Bézier fitting and parallel curves. Licences and features should be confirmed before adoption.
- Whether any maintained Rust crate does robust Bézier-level Boolean operations as of late 2026 was not researched.
- No source was read on SVG variable-width stroke proposals in the SVG 2 process.

## 9. Differentiable or optimisation-based fitting to reference drawings

### Takeaway
Differentiable vector rasterisers exist and have become much faster (Bézier Splatting, NeurIPS 2025, reports 30× forward and 150× backward speed-ups over DiffVG for open curves), and differentiable 3D-curve renderers (Diff3DS) show multi-view fitting of Bézier curves is feasible. For a low-dimensional parametric template, though, landmark- and silhouette-based fitting with ordinary optimisers is likely enough and far less fragile.

### Cited Findings
- DiffVG's repository is Apache-2.0, has 44 commits, 62 issues and 5 pull requests listed, and its install notes reference Python 3.7 with a CMake/pybind11/PyTorch build. Demos cover circles, ellipses, rectangles, polygons, curves, paths and gradients. [V] — [BachiLi/diffvg](https://github.com/BachiLi/diffvg)
- Bézier Splatting (Liu, Zhou, Zhao & Huang; arXiv March 2025, NeurIPS 2025 poster): samples 2D Gaussians along Bézier curves and rasterises by Gaussian splatting, giving positional gradients at boundaries; reports 30× faster forward and 150× faster backward passes than DiffVG for open curves (an earlier version said 20× forward); adds pruning and densification of curves; converts to standard SVG. Figures are the authors' own. [S] — [arXiv 2503.16424](https://arxiv.org/abs/2503.16424), [NeurIPS 2025 poster](https://neurips.cc/virtual/2025/poster/117178)
- Diff3DS (2024) optimises 3D rational Bézier curves through a differentiable perspective projection and rasterisation to obtain view-consistent 3D sketches. [S] — [arXiv 2405.15305](https://arxiv.org/abs/2405.15305)
- 3Doodle (2024) fits 3D Bézier feature lines and view-dependent contour primitives to multi-view images without a mesh. [S] — [3Doodle](https://arxiv.org/html/2402.03690v1)
- El Mqirmi & Aigerman (2025) list "fitting 3D models to sketches and caricatures" among applications of view-dependent deformation fields. [V] — [arXiv 2504.05544](https://arxiv.org/abs/2504.05544)

### Inferences
- **Could parameters be fitted to existing drawings to learn their distribution? In principle yes, in three tiers of increasing cost**: (1) *Landmark fitting*: run an anime landmark detector on reference faces (section 10), then solve for the model parameters that best reproduce the landmark positions; with a few dozen parameters this is a small non-linear least-squares problem solvable with finite differences. It recovers proportions (eye-line height, eye size and spacing, jaw width, chin length) and, over a corpus, gives means, ranges and correlations for the sliders. (2) *Silhouette/edge fitting*: compare the rendered template's line map or silhouette with an edge map of the reference via a distance-transform (chamfer) loss; still workable with gradient-free optimisers at this dimensionality. (3) *Differentiable rendering* (DiffVG or Bézier Splatting): needed only when fitting many free control points; it is prone to local minima, and unconstrained it produces exactly the unstructured point soup the project is trying to avoid, so it must optimise model parameters, not raw points.
- **Fitting is most valuable for the view corrections** (section 4): given a professional turnaround sheet with front, three-quarter and side drawings of one character, fit the 3D-consistent base to all three, and the residual per view *is* the cheat table. A modest set of turnaround sheets could yield an averaged correction table. This is an inference; no source doing this for anime faces was found.
- **DiffVG is a liability as a dependency**: old build chain, research code, low commit count. Treat it as unmaintained unless the commit history says otherwise. If differentiable rendering is wanted, a small custom soft rasteriser over the model's own few hundred curve samples, in PyTorch or JAX, is a weekend-scale alternative for an agent to write and verify.
- **Data and licensing**: fitting to existing drawings learns proportions, which are not themselves copyrightable expression in the way the drawings are, but the corpus source and its terms still matter for an open-source project. Not researched here.
- **Difficulty**: tier 1 easy to moderate; tier 2 moderate; tier 3 hard to make robust. None is required for a first working model.

### Gaps
- DiffVG's last commit date and whether it supports per-control-point stroke width were not shown on the fetched page.
- Bézier Splatting's code availability and licence were not checked.
- Other 2024–2026 differentiable SVG renderers were not surveyed beyond the one found.
- No paper was found that fits a *parametric anime character template* to drawings to learn slider distributions.

## 10. Verification loop for AI agents

### Takeaway
Off-the-shelf perceptual checks are weak exactly where the project is hardest: anime landmark detectors are documented as near-frontal only and struggle with profiles and round eyes, anime aesthetic scorers have no published human-agreement figures and known biases, and a 2026 study finds VLM judges of SVG respond unevenly across error types. The reliable checks are analytic ones computed from the model's own geometry, backed by human-approved golden references.

### Cited Findings
- hysts/anime-face-detector: 28 landmarks via HRNetV2, with Faster R-CNN or YOLOv3 face detection; MIT code with vendored Apache-2.0 OpenMMLab code; requires Python 3.12+ and PyTorch 2.2+, and since v0.1.0 has no OpenMMLab runtime dependency; described as handling "near-frontal anime faces"; no accuracy metrics on the page; originally published 2021. [V] — [anime-face-detector](https://github.com/hysts/anime-face-detector)
- MDFLD: 68-point landmark detector for cartoons, caricatures, paintings and photos (ICASSP 2024 paper; v3 news dated November 2026, using frozen DINOv3 features). Normalised mean error on the CariFace caricature test set (1,560 images): v1 6.70, v2 5.03, v3 4.64 percent of outer-eye-corner distance; on 1,462 synthetic anime faces with approximate labels: v3 5.09 vs v2 6.30. The authors caution these sets were used to choose v3. Stated limits: "Non-human characters, profile views and covered eyes are still hard"; faces should be roughly upright; six points per eye gives round cartoon eyes an almond shape. "Research use only"; v3 weights under the DINOv3 licence; needs a CUDA GPU by default. [V] — [MDFLD](https://github.com/zenonLEE/MDFLD)
- Anime aesthetic scorers (aesthetic-shadow v1/v2, waifu-scorer v3, skytnt anime-aesthetic, others): model cards give no validation against human ratings; aesthetic-shadow-v2 is CC-BY-NC-4.0 and a backup repository carries a notice that the original author planned to take it down. [S] — [aesthetic-shadow-v2](https://huggingface.co/shadowlilac/aesthetic-shadow-v2), [waifu-scorer-v3](https://huggingface.co/Eugeoter/waifu-scorer-v3), [backup notice](https://huggingface.co/NeoChen1024/aesthetic-shadow-v2-backup)
- Community write-ups report these scorers are biased toward high contrast and saturation, and that waifu-scorer and a PonyV7 classifier rate AI-generated images above comparable hand-drawn ones; these are informal tests, and I could not pin each statement to a specific page among the results. [S] — [aesthetic tech talk archive](https://lapis-8g5.pages.dev/experiments/archive/2025-03-aes-tech-talk), [eval basics post](https://huggingface.co/gustproof/sd-models/raw/main/posts/eval_basics.md)
- SVG-Score (arXiv, September 2026): CLIPScore "aligns only partially with human judgment" for text-to-SVG; off-the-shelf VLM judges are "more sensitive" to errors than CLIP-based scores but "respond unevenly across error types and SVG styles". [V] — [arXiv 2609.03806](https://arxiv.org/abs/2609.03806)
- From the same paper per search summary: fine-tuning a VLM judge raised Spearman correlation with human ratings from about 67.8 to 74.9 over its zero-shot backbone. [S] — [arXiv 2609.03806](https://arxiv.org/abs/2609.03806)
- VectorGym (2026) proposes a VLM-as-judge metric for SVG tasks validated by human correlation studies; MUSE (text-to-CAD, 2026) reports judge-human correlation around 0.71 at sub-criterion level and about 0.83 at design-instance level for the best judges on rendered SVG. [S] — [VectorGym, arXiv 2603.29852](https://arxiv.org/abs/2603.29852), [MUSE, arXiv 2605.28579](https://arxiv.org/pdf/2605.28579)

### Inferences
- **The generator already knows its own landmarks.** Because every landmark is a named quantity in the model, on-model checks do not need a detector: compute ratios directly (eye-line height / head height, eye width / face width, inter-eye gap / eye width, mouth and nose positions, head-to-body ratio, limb ratios) and assert them against target ranges. These tests are deterministic, fast and exact, which is what an agent loop needs.
- **Tier 1, analytic invariants (reliable)**: target ratios; left-right symmetry of the front view to numerical tolerance; cross-view consistency (each landmark's 2D position in every view equals the projection of its 3D point plus the declared correction; back view outline equals mirrored front outline); monotonic and bounded response of every landmark to every slider; no self-intersecting outlines; closed fills; containment (iris inside sclera clip, features inside face contour, with margins); draw-order constraints; continuity of every control point as yaw sweeps (no jumps except at declared swaps); stable path/point counts per part.
- **Tier 2, raster regression (reliable once a human has approved references)**: render to PNG and compare with golden images (pixel difference or structural similarity), silhouette overlap against approved silhouettes, and a slider-sweep contact sheet. This catches unintended changes; it cannot say whether a new design is good.
- **Tier 3, perceptual checks (weak, use as smoke tests)**: an anime landmark detector on the front and mild three-quarter renders, comparing detected landmarks with the model's own (a large disagreement means the render does not read as a face); do not use it for side or back views given the documented limits. Aesthetic scorers should not gate anything. VLM critique is useful for gross failures ("the eye is outside the head", "the mouth is missing") and unreliable for fine proportion judgements.
- **All of the perceptual models were trained on shaded raster illustrations.** Their behaviour on flat-colour line-art SVG renders is unknown and could be worse; a quick calibration on a few dozen known-good and deliberately broken renders is needed before trusting any of them.
- **Human gates remain necessary** at a few points: approving the base head in each key view, approving each view-correction table, and approving each eye and hair preset. The design goal is to make those approvals few and durable (frozen as golden references), with everything downstream checked analytically.

### Gaps
- No evidence was found on landmark-detector accuracy on synthetic flat vector renders, or on any detector for anime faces in true profile.
- No published correlation between anime aesthetic scorers and human ratings was found.
- VLM-judge numbers come from general SVG/CAD benchmarks, not character art; VectorGym and MUSE were not opened.
- No full-body anime pose/proportion estimator was researched for body checks.

## 11. Recommendation inputs: per-architecture authoring, code, failure modes, animation suitability

### Takeaway
The architecture best supported by the evidence is a hybrid: a small 3D parametric landmark-and-curve rig as the single source of truth for proportions and placement, 2D part shapes with a few authored key views blended over view angle for silhouettes and stylised parts, and an explicit table of per-view corrections. Pure 2D templates cannot keep views in agreement, and mesh contour extraction is too heavy and too noisy for interior face lines.

### Cited Findings
- Three or four hand-drawn key views per stroke were enough for a rotatable 2.5D model, with mirrored views derived automatically; interior lines, concave shapes, hair and wrap-around occlusion are that method's documented failures. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- 2D conventions for facial animation carry over to 2.5D models directly because the animator draws the desired appearance without solving for a 3D shape. [V] — [Rivers et al. 2010 (PDF)](https://www-ui.is.s.u-tokyo.ac.jp/~takeo/papers/alec_siggraph2010_cartoon.pdf)
- Live2D-class rigs give about ±30 degrees of head turn from one drawing via hand-deformed lattices. [S] — [Standard Parameter List](https://docs.live2d.com/en/cubism-editor-manual/standard-parameter-list/)
- Robust contour visibility from meshes was still an open research topic addressed by a 2023 TOG paper, and Blender's SVG paths from Freestyle/Line Art carry documented caveats. [V]/[S] — [ConTesse](https://dgp.toronto.edu/~hertzman/contesse/), [Freestyle SVG Exporter manual](https://docs.blender.org/manual/en/4.1/addons/render/render_freestyle_svg.html)
- Feature lines as fixed 3D Bézier curves plus view-dependent contours of simple primitives is a published, compact representation. [S] — [3Doodle](https://arxiv.org/html/2402.03690v1)
- View-specific corrections blended over viewpoint are the established answer to non-3D-consistent cartoon drawing. [S]/[V] — [Rademacher 1999](https://history.siggraph.org/?p=116416), [Fukusato & Maejima 2021](https://arxiv.org/abs/2103.15472)
- kurbo supplies stroke expansion, offsetting and cubic fitting under Apache-2.0/MIT but not variable-width strokes or Booleans. [V] — [kurbo docs](https://docs.rs/kurbo/latest/kurbo/)

### Inferences
All entries below are my assessment from the findings above; line counts are rough order-of-magnitude estimates for core logic excluding authored data and tests.

| | A. Pure 2D per-view templates | B. 2.5D (key-view shapes + 3D anchors) | C1. 3D mesh + contour extraction | C2 / hybrid. 3D landmark-and-curve rig + view-keyed 2D shapes + corrections |
|---|---|---|---|---|
| Hand-authored | Every part and every slider delta in each of 4 views; anchors per view | Every stroke in 3–4 views with correspondence; overlap/visibility ranges; slider deltas per key view | A parametric anime head/body mesh with morph targets; edge marks for feature lines; view-dependent shape keys | 3D landmark positions and slider-to-landmark maps; feature curves in 3D; head/hair silhouette shapes in 3–4 views; correction table; eye and hair presets |
| Code (core) | ~1.5–3k lines | ~3–6k lines | ~1–2k lines of Blender scripting plus ~1–2k for path cleanup; heavy runtime dependency | ~4–8k lines |
| Main failure modes | Views drift apart; no in-between angles; slider semantics differ per view | Interior lines merging into silhouette; hair and concave shapes; popping; authoring volume; patent to check | Noisy or wrong interior face lines; needs cheats anyway; GPL subprocess; mesh authoring is beyond an agent's reliable reach | Silhouette-to-interior-line joins (cheek/jaw); visibility rules; correction tables need taste or references |
| View consistency | By discipline only | Placement consistent by construction; shape by hand | Consistent by construction, but wrong for anime without corrections | Placement and proportions by construction; shape by few key views; cheats explicit and testable |
| Head turns | No (discrete views only) | Yes, continuous | Yes, continuous | Yes, continuous |
| Blink, lip-sync | Easy (2D blend shapes) | Easy | Awkward (3D shapes, re-extract lines) | Easy (2D blend shapes on named curves) |
| Body, walk cycles | Per-view rigs, cut-out style | Good for limbs as anchored strokes; clothing occlusion weak | Good, standard skeletal animation | Good: skeleton is 3D, limbs are ribbons, order from depth |
| Agent verifiability | Weak (nothing to test views against) | Medium (anchor residuals) | Weak (output is unstructured polylines) | Strong (ratios, projections and continuity are all analytic) |

- **Why the hybrid addresses the two known failures.** "Base proportions" stop being a matter of placing Bézier points: they are a short list of named 3D landmarks with numeric ratio targets that an agent can compute and test. "A turnable head" stops being a drawing problem: landmark positions in any view are a rigid rotation and projection, and only a few silhouette shapes need per-view authoring, with the rest being projected curves or anchored 2D parts.
- **Suggested build order by risk**: (1) 3D landmark rig for the head with ratio tests and an orthographic projector, drawn as dots and guide lines in four views; (2) head outline as a view-keyed shape (front, three-quarter, side; back by mirroring) with jaw sliders, plus neck; (3) eyes as a parametric module with front and three-quarter and profile forms; (4) nose, mouth, brows, ears as anchored parts with correction table and discrete swaps; (5) variable-width stroke emitter and semantic SVG structure; (6) hair as clump ribbons on 3D guides with a few hand-designed styles; (7) body skeleton with limb profiles; (8) clothing; (9) optional fitting to reference turnarounds. Steps 1–2 test the core hypothesis cheaply before any content investment.
- **Where 3D tools still help**: use an existing 3D anime model rendered in Blender as an offline reference to initialise landmark positions per view and to sanity-check the projector, not as part of the runtime.
- **Frank difficulty ranking, hardest first**: hair that looks designed; view corrections that look right in three-quarter; eyes that look appealing across the slider range; clothing variety; cheek/jaw silhouette joins; body hands and feet; stroke outlines and Booleans; the 3D landmark rig and projection; SVG structure. The top three are aesthetic problems with weak automated verification, so they will consume human review time regardless of architecture.

### Gaps
- No existing open-source project was found that implements the hybrid as described, so there is no reference implementation to measure effort against; the line-count figures are estimates.
- The patent status and claim scope of US 8,791,942 relative to a design that uses 3D anchors with 2D key-view shape interpolation need a proper check.
- I did not find evidence on how many key views an anime head outline needs in practice for acceptable in-between angles; Rivers' three-to-four figure comes from simpler Western cartoon characters.
- Search volume for this note exceeded the usual budget, yet several primary documents remained unread (Guilty Gear Xrd slides, Inochi2D parameter docs, Rademacher's paper text, the Bénard & Hertzmann full text); claims depending on them are marked [S] or listed as gaps above.
